# Step-by-step implementation plan

Status: proposed plan, 7 October 2026. This plan implements the browser/Java direction in `CONTRACT.md` and the operational outcomes in `PROJECT_ROADMAP.md`. The repository has build/client skeletons and the v1 contract package; game behavior and operations remain future work. [Architecture and module responsibilities](ARCHITECTURE.md) define the target structure.

## Outcome and estimates

Release 1 is a playable browser game: one map, room codes, 2–4 guest players, server-authoritative movement and bombs, one match result, reconnect to the same live process, HTTPS/WSS, Terraform-provisioned single EC2, reproducible deployment, off-host failure detection, measured load, and a recovery report. It does not promise preservation of active matches after a process or instance failure.

Do the steps in order. A step is complete only when its evidence and gate pass; do not advance because the calendar says to. The work is roughly **180–280 person-hours** before the code audit, asset work, and learning variance are known. At 12–15 hours per week for one person, reserve roughly **16–24 calendar weeks**, including integration and repair time. Re-estimate after steps 1 and 8. A larger team can split the indicated independent work, but shared contract changes and final integration remain serial.

## 1. Establish the source and scope

1. **Audit sources and rights.** List any original Java game repository, code license, asset licenses, and actual build commands. If reuse is unclear, implement the small rule set with original/simple placeholder art. *Purpose:* avoid a late rewrite or a portfolio demo with unusable assets. **Gate:** a documented source/asset inventory and a clean build of any code being reused.
2. **Resolve the document conflict.** Record an ADR that release 1 has a TypeScript/Phaser browser client and Java server, as `CONTRACT.md` states. Verify that `PROJECT_ROADMAP.md` and `STACK.md` label desktop, React, accounts, PostgreSQL, and Redis as later or conditional. Start a minimal CI workflow for document/schema checks. *Purpose:* give the team one release target and an early change gate. **Gate:** no document calls the desktop client the required MVP.
3. **Freeze the playable rules.** Define map grid, movement cadence, collisions, bomb fuse/range, chain reactions, simultaneous deaths, draw, room state transitions, and match timeout. *Purpose:* make deterministic server tests possible. **Gate:** example input sequences have an unambiguous expected state and winner/draw.
4. **Set project limits.** Record team hours, region, monthly spending ceiling, maximum live rooms/players, and demo operating hours. Create the first AWS estimate and budget before provisioning. *Purpose:* align implementation and cloud costs with available time. **Gate:** signed-off scope and a calculator export or equivalent itemized estimate.

## 2. Make the wire contract executable

5. **Define the MVP API and amend the contract.** Replace the login/leaderboard assumption for release 1 with guest session, create room, and get room. Specify request/response status codes, guest cookie issuance/expiry/renewal, idempotent reuse of a still-valid session, SameSite/Origin rules, and typed errors in `contracts/openapi.yaml`. Mark old account endpoints as future in `CONTRACT.md`. *Purpose:* keep account storage out of the first release while preserving one clear REST boundary. **Gate:** no implementation starts until `CONTRACT.md` and OpenAPI agree on the MVP endpoints.
6. **Define WebSocket v1 schemas and amend examples.** Add command/event envelopes, required `version`, `requestId`, success acknowledgement/error correlation, bounded request-ID retry semantics, server timestamp, event sequence or tick number, full snapshot, invalid-version behavior, draw result, and enum/status rules. Define reconnect/resync messages, credential lifetime, payload limits, and errors. *Purpose:* prevent client/server disagreement and silent divergence after missed events. **Gate:** `CONTRACT.md` examples and valid/invalid JSON fixtures agree with schemas; missing versions are rejected as specified.
7. **Build cross-language contract checks.** Map schemas to Java DTOs in `protocol-java/` and TypeScript types/validators in `client-web/src/protocol/`. Test both using the same JSON fixtures, including snapshot plus deltas, sequence gaps, duplicate/out-of-order events, reconnect resync, and duplicate `PLACE_BOMB` request IDs. *Purpose:* detect drift without sharing implementation code. **Gate:** an incompatible fixture fails both checks and a reconstructed client state matches the server snapshot.

## 3. Create a testable game core

8. **Initialize the monorepo and CI.** Add Gradle wrapper/toolchain, Vite/TypeScript/Phaser, formatting, build/test commands, and `.github/workflows/ci.yml`. CI validates contracts, Java, and browser build on every pull request. *Purpose:* make each later change reproducible. **Gate:** a clean checkout passes CI with no local-only setup.
9. **Implement pure game state and `step`.** Build map, players, bombs, tick clock, ordered command application, explosion propagation, damage, and winner/draw in `game-core/`. No Spring or network types enter this module. *Purpose:* make authority and rules deterministic. **Gate:** same initial state, seed, tick, and commands produce the same result twice.
10. **Test boundary rules.** Cover blocked movement, duplicate/late commands, bomb limit, chain reaction, simultaneous deaths, disconnect policy, and match timeout. Add replay fixtures for at least one complete match. *Purpose:* prevent protocol timing from changing game outcomes. **Gate:** headless replay reaches the expected final state and survives refactor.

## 4. Build the server and browser as one vertical slice

11. **Implement guest/room REST.** Issue an opaque expiring guest credential in a Secure/HttpOnly/SameSite cookie, create/get rooms, verify expected `Origin` for mutations, and enforce guest issuance plus room/session rate limits. *Purpose:* let a browser join without password or database work. **Gate:** unauthenticated, cross-origin, session-fixation, and over-limit requests fail with documented codes.
12. **Implement room runtime.** Queue validated commands per room, mutate each room serially on a fixed tick, and expire empty/finished rooms after a documented TTL. Put bounds on queues and processing work. *Purpose:* prevent races and unbounded memory growth, including rooms left by synthetic checks. **Gate:** two bot clients can create, join, ready, start, leave, and finish a match locally; abandoned rooms are removed.
13. **Implement the WebSocket gateway.** Validate the upgrade `Origin`, session, frame size, version, message type, and input rate; use one serialized sender and bounded output queue per connection. Correlate each command to an acknowledgement or error and deduplicate recent request IDs. Emit snapshots/events from the room runtime. *Purpose:* preserve room authority when clients are slow or hostile. **Gate:** spoofed IDs, oversized frames, invalid versions, duplicates, and excessive commands cannot alter game state or grow queues indefinitely; all clients agree with authoritative state after each tested event.
14. **Implement minimal browser play.** Add a simple DOM lobby for guest, create/join/ready, errors, and result; Phaser renders the one map, players, bombs, explosions and sends input commands. Keep damage and winner logic out of the client. *Purpose:* satisfy the browser contract with the smallest usable interface. **Gate:** two humans in separate browser sessions finish a match and see the same result.
15. **Implement synchronization and reconnect.** Apply snapshot then ordered events in the client reducer; on a gap or reconnect, resync with a full snapshot. Retain a player slot for a documented short window on the same process. *Purpose:* make real network interruptions recover cleanly. **Gate:** a 5–10 second network cut rejoins the same player; server restart ends the match with a clear UI message.

## 5. Add operability before public deployment

16. **Package and run locally.** Build a non-root server image and Compose setup with Caddy serving the browser and proxying `/api` and `/ws`. Add liveness/readiness endpoints, a persistent Caddy data mount (EBS-backed in AWS), and graceful drain behavior. Use Caddy HTTP-01 with a domain and public TCP 80/443 in AWS. *Purpose:* make local and cloud releases behave the same. **Gate:** a clean machine can run the documented Compose command and complete a match; the public deployment later renews a trusted certificate.
17. **Instrument the application.** Add structured logs with release SHA and correlation IDs, room/connection counts, rejected commands, tick duration and overruns, send queue pressure, reconnect outcomes, JVM/host resource measures. Define the CloudWatch Agent config and scoped instance-role permissions for forwarding selected data. Set log retention and avoid player/room IDs as metric dimensions. *Purpose:* diagnose gameplay failures without uncontrolled telemetry cost. **Gate:** a bot match produces useful logs and dashboard data; no credential appears in logs.
18. **Define service objectives and alerts.** Specify a scheduled synthetic success indicator using two guest clients to create/join/start and clean up a disposable match. Record operating hours, denominator, minimum sample size, threshold after baseline, missing-data policy, latency target under stated load, and who responds. Set alarms for failed/missing checks, instance status, and persistent game errors; verify delivery to a real operator. *Purpose:* detect a broken game even when the host cannot report its own health. **Gate:** a deliberately stopped app triggers an off-host alert and a runbook action; no attainment claim is made before the minimum sample is met.

## 6. Provision and release on AWS

19. **Bootstrap Terraform state.** Create and document a separate S3 state bucket with restricted access, encryption, versioning, and lockfile support; pin Terraform/provider versions. Keep state and saved plans out of Git. *Purpose:* make team changes safe and recoverable. **Gate:** a second operator can initialize and plan without copying a local state file; concurrent lock acquisition is blocked and an unauthorized principal cannot read state.
20. **Provision the demo stack.** Terraform creates VPC, public subnet, route, security group, EC2/EBS, Elastic IP, IAM/SSM, ECR, CloudWatch Agent configuration/logs/alarms, SNS, budget, and DNS if the domain is in Route 53; otherwise document the external DNS record. Expose public TCP 80/443 for Caddy HTTP-01 and HTTPS; use SSM for management. Preserve Caddy certificate data across container releases; host replacement reattaches the Elastic IP and reissues a valid certificate. A protected operator manually applies a reviewed plan; check drift before release. *Purpose:* recreate the same small environment and know its cost. **Gate:** HTTPS/WSS uses a trusted certificate, repeat `plan` shows no unexpected change, and destroy checklist identifies residual billable resources.
21. **Publish immutable artifacts.** Protected main builds a Spring Boot image and a Caddy image containing the Vite browser build from the same commit. GitHub Actions uses scoped OIDC credentials to publish both to ECR and records both digests and the contract version in a release manifest. *Purpose:* trace both halves of a running release to source. **Gate:** no long-lived AWS key in CI; both image digests resolve to the same commit.
22. **Automate a controlled release.** A human chooses a release manifest containing both image digests. A script drains new matches, waits for current matches to finish or aborts at deadline, updates both Compose digest pins, waits for readiness, runs public HTTP and WebSocket smoke checks, and restores both previous pins if the new release is unhealthy. Document the brief single-host interruption and the loss of in-memory matches after a crash. *Purpose:* demonstrate a repeatable rollback while respecting live matches and protocol compatibility. **Gate:** a deliberately bad release rolls back with recorded detection and recovery times.

## 7. Prove performance and recovery

23. **Run realistic load.** Use a separate load generator whose bots create/join/ready/move/bomb/finish, not idle sockets. Test increasing room counts, repeat a stable point, then soak for 60 minutes. Record instance type, region, release, RTT, bot behavior, tick p95/p99, client-observed latency, disconnects, queue depth, heap and cost. *Purpose:* support a bounded capacity claim. **Gate:** publish raw results, failed runs, bottleneck, and the largest stable measured load.
24. **Run three recovery drills.** Kill the app, deploy an unhealthy release, and replace the host from Terraform/ops instructions. Measure detection, recovery, manual actions, and lost state. *Purpose:* distinguish restart, rollback, and rebuild capabilities. **Gate:** one concise incident report per drill; each claim matches observed evidence.
25. **Verify the demo from outside the team.** Have a new machine/browser follow README instructions; test two real networks, at least ten complete matches, bad inputs, and reconnect. *Purpose:* expose hidden local setup and networking assumptions. **Gate:** a reviewer can reach the demo or reproduce it from the documented release.

## 8. Present the work honestly

26. **Prepare portfolio evidence.** Publish an architecture diagram, protocol decision, Terraform plan/apply evidence with sensitive data removed, CI run, deployment/rollback timeline, dashboard screenshots, load report, incident reports, cost estimate versus actual spend, and a 3–5 minute demo. State which parts each contributor built and operated. *Purpose:* make CV claims inspectable. **Gate:** each CV bullet points to a real artifact and measured number.
27. **Clean up.** Verify the destroy path, retained ECR images/logs/state bucket, and expected continuing charges. Keep only deliberate demo resources. *Purpose:* prevent a portfolio project from creating an unmanaged bill. **Gate:** recorded final resource inventory and cost review.

## Parallel work with a team

After steps 1–7 settle the contract, one contributor can own `game-core/` while another builds `client-web/` against fixtures. The server WebSocket gateway can begin against a fake core, then integrate with the real core at step 12. A separate contributor can prepare CI, Terraform state, cost estimate, and runbook drafts early. Contract changes, room semantics, and release acceptance need one designated integrator; avoid concurrent independent edits to those boundaries.

## Scope control

If the project slips, first reduce art, animations, map count, and optional events. Keep a single reliable game mode. Defer React, accounts, leaderboard, PostgreSQL, Redis, ECS, and static CDN delivery until the first release meets its gates. Preserve contract tests, server authority, bounded queues, real browser play, IaC, off-host monitoring, release/rollback, and evidence. ECS is a valid later exercise if the team wants to compare operational responsibility and cost; it does not require a multi-node game, but any multi-task design must solve room ownership and reconnect routing.
